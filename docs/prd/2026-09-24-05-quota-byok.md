# PRD：配额与自备 Key 体验（Quota & BYOK UX）

**产品：** 墨语 · inkara  
**文档编号：** PRD-05  
**日期：** 2026-09-24  
**状态：** Draft  
**设计原则对齐：** `.impeccable.md`（失败写在纸上；不做成运营弹窗）

---

## 1. Summary

正式环境未配置用户自备 API Key 时，每日仅 2 次免费问答；超出或未配置时的错误已写在纸上，但**缺少预见、校验与引导节奏**，用户容易在「用尽」时感到被打断，或在设定里填错 Key 却要等到提交才失败。本 PRD 改善配额可见性、用尽后的纸上引导、以及 BYOK 配置反馈——仍经本站 `/api/ask` 代发，不改计费模型。

## 3. Background

### 现状

| 项 | 实现 |
|----|------|
| 免费额度 | `FREE_DAILY_LIMIT = 2`，仅 `production` 且无用户 Key 时计数（`quota.ts`） |
| 存储 | IndexedDB 本机计数；清站点数据可重置 |
| 用尽文案 | `quotaExceeded` → 写在纸上 |
| 缺 Key | `missingKey` 等错误路径 |
| BYOK | 设定中 apiKey / baseUrl / model；随请求传服务端 |

### 痛点

1. 用户不知道「还剩几次」——两次很快用完，第三次才被告知。  
2. 用尽后要自己找设定；纸上提示未形成「轻触可去设定」的清晰动作（若已有重试，需与「去设定」区分）。  
3. Key / Endpoint 填错时，反馈可能是上游晦涩错误，不像「纸说人话」。  
4. 开发模式不限次，易与正式行为认知不一致（文档已有说明；产品内可在设定轻微提示）。

### 为什么现在做

BYOK + 配额已是正式环境的闸门；闸门体验差会直接伤害「想认真用的人」，且改动面主要在文案与设定，适合单独立项。

---

## 4. Objective

**目标：** 使用免费额度的人**提前提到余量**；用尽或 Key 有问题时，纸面用一句话说明原因与下一步，设定里能较快确认「Key 能用」。

### Key Results

| KR | 指标 | 目标 |
|----|------|------|
| KR1 | 免费路径下，第 1、2 次成功前提示余量或「今日免费 n/2」 | 至少在设定页常驻；纸面可选轻提示 |
| KR2 | 用尽后纸上文案 | 含「设定中填写自己的 API Key」且可一动作打开设定 |
| KR3 | BYOK 保存后可「试一下」 | MVP：保存时本地非空校验；v1.1：可选一次轻量探测请求 |
| KR4 | 不增加服务端防刷指纹 | 仍为本机配额（产品决策不变） |

## 7. Solution

### 7.1 UX

**A. 设定页（常驻，MVP 必须）**

在 BYOK 区块上方或下方增加只读状态行：

- 已填 Key：`使用自己的接口 · 不受每日免费次数限制`  
- 未填 Key + production 行为说明：`今日免费问答：{used}/{limit}`（开发环境：`开发模式不限次`）  
- 简短说明：正式环境无自备 Key 时每日 2 次；数据仅存本机。

**B. 纸面用尽 / 缺 Key（MVP 必须）**

- 保持「写在纸上」；  
- 文案可点或纸面轻触：**打开设定**（优先）与可选「稍后」；  
- 与网络错误重试区分：配额错误不应假装「再试一次」能好（除非已改 Key）。

**C. 余量预告（MVP 可选增强）**

- 当 `usesFreeQuota && remaining === 1` 且本轮成功结束后，dock 或纸角极淡提示「今日免费还剩 1 次」一次即可，不每帧闪烁。

**D. BYOK 反馈（MVP + v1.1）**

- MVP：apiKey trim 为空时不允许「假装已配置」；baseUrl 若填则需为合法 URL 形态。  
- v1.1：设定内「试写一笔」或「检查连接」按钮 → 发最小请求或 `/models` 类探测（视上游兼容性；失败时人话错误）。

### 7.2 Key Features

| ID | 功能 | 阶段 |
|----|------|------|
| F1 | 设定页配额/BYOK 状态行 | MVP |
| F2 | 用尽纸文案 + 打开设定 | MVP |
| F3 | 配额错误与可重试错误分流 | MVP |
| F4 | 字段基本校验（非空、URL） | MVP |
| F5 | 剩 1 次成功后的一次余量提示 | MVP 可选 |
| F6 | 连接探测 | v1.1 |
| F7 | 服务端配额 / 账号 | 不做 |

### 7.3 User Stories & Acceptance Criteria

**Story A**  
As a 试用用户, I want 在设定里看到今日还剩几次, so that 我不会突然用尽。

- [ ] production + 无 Key 时显示 used/limit  
- [ ] 有 Key 时不显示免费计数压力文案（改为自备接口说明）  
- [ ] 中英文齐全

**Story B**  
As a 用尽免费次数的用户, I want 纸上告诉我去设定填 Key, so that 我能继续。

- [ ] 文案含设定指引  
- [ ] 提供打开设定的明确操作  
- [ ] 填入 Key 后下一次提交走 BYOK，不再拦配额

**Story C**  
As a 填写自备 Endpoint 的用户, I want 明显格式错误被当场指出, so that 少一次失败提交。

- [ ] 非法 URL 在设定内提示  
- [ ] 不把原始 stack / 供应商 HTML 写满纸面；映射为短句

### 7.4 Non-Goals

- 提高或动态调整免费次数（产品策略变更需另批）  
- 服务端强制配额、设备指纹  
- 登录、订阅、支付  
- 多 Key 管理、团队空间

### 7.5 Technology

- `src/lib/quota.ts`、`settings.ts`、`SettingsPanel.tsx`  
- `InkPage.tsx` 错误展示与「打开设定」回调  
- `src/app/api/ask/route.ts`：错误码稳定映射（如 `quota_exceeded`、`unauthorized`、`upstream`）便于前端人话  
- i18n 文案更新  
- README 与设定说明保持一致

### 7.6 Security & Privacy

- Key 仍仅存本机 IndexedDB；请求经服务端转发时注意不写日志明文 Key（维持或加强现有红线）。  
- 「检查连接」不得在客户端把 Key 发往第三方分析。

### 7.7 Assumptions

- 2 次免费策略短期不变。  
- 用户可接受本机清数据即重置计数（诚实说明即可）。
